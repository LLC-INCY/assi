# Инструменты 0.4.0

В активном сеансе доступны компактные иконки управления/обзора/рисования, меню экрана, клавиатуры и звука, файлы, полноэкранный режим и завершение. В меню «Ещё» — сохранение PNG с пометками. Обе стороны должны использовать 0.4.0.

Общие пометки передаются по тому же защищённому каналу: перо/стрелка/рамка,5 цветов,3 толщины, отмена своей последней пометки и очистка всей доски. На macOS/Windows у владельца также есть наложение поверх основного рабочего стола; Linux/Android видят пометки внутри Асси.

Системный звук владелец включает отдельно в меню динамика. Зритель отдельно включает прослушивание и регулирует громкость. Микрофон не используется. Capture macOS 13+/Windows; воспроизведение на платформах с WebAudio. Capture Linux/Android пока отсутствует.

Клавиатура включает F1–F12, служебные клавиши, сочетания и поле Unicode для кириллицы/IME. «Из буфера» заполняет поле, «Отправить» вводит его на удалённой стороне. Это не автоматическая синхронизация системного буфера.

Монитор/качество выбирает владелец. Смена монитора разрешена только в сеансе просмотра; при управлении нужно переподключиться без управления. Качество low/balanced/high задаёт 1280/1920/2560px и целевые 6/8/12FPS. Полная частота зависит отCPU/сети.

Состояние и ограничения: [матрица функций](SESSION-TOOLS.md), [звук](AUDIO.md), [наложение](OVERLAY-NOTES.md).

# Подключения и файлы в Асси 0.3.0

## Подключение в общей сети

На устройстве, экран которого нужен, выбрать «Предоставить доступ» → «Напрямую».
Указать IP этого устройства в общей сети; 127.0.0.1 подходит только для локальной
проверки. Передать созданное приглашение ожидаемому участнику по доверенному каналу.
На втором устройстве: «Сеансы» → «Подключиться» → вставить приглашение.
Владелец подтверждает конкретный запрос; мышь/клавиатура разрешаются отдельно.

Приглашение содержит секрет, действует для одного подключения и не сохраняется.
Нельзя публиковать его в открытом доступе. Имя второго участника указано им самим
и не является удостоверенной идентичностью.

## Подключение через свой сервер

Relay позволяет обеим сторонам подключаться исходящим соединением, когда они
находятся за NAT. Автоматического выбора маршрута или UDP hole punching пока нет.
Сначала администратор запускает сервер на доступной обеим сторонам машине:

```sh
cargo build --release -p assi-relay
# По умолчанию bind только loopback. Это пример локального запуска:
./target/release/assi-relay --bind 127.0.0.1:4788 --identity ./assi-relay-identity.json
```

Сервер печатает публичную конфигурацию `assi-relay://…` с адресом и сертификатом.
Владелец экрана выбирает «Через сервер» и вставляет эту конфигурацию; затем передаёт
обычное приглашение `assi://…` участнику. В нём уже включён маршрут.
Настройка публичного IP, firewall, службы и эксплуатации выполняется на выбранном
сервере отдельно. Общедоступный сервер Асси не развёрнут. Подробности и параметры:
[`crates/assi-relay/README.md`](../crates/assi-relay/README.md).

Внутри соединений с relay устанавливается дополнительное TLS-соединение между
конечными устройствами. Сервер видит сетевые адреса, объём и время трафика, но не
содержимое экрана, ввода и файлов. Сервер может прервать соединение; доверие к
устройству основано на приглашении, полученном по доверенному каналу.
Короткий числовой код из адресной книги пока не заменяет приглашение: регистрация
устройств, аккаунты и безопасный поиск по коду ещё не реализованы.

## Передача файла

В активном сеансе открыть блок «Файлы» → «Отправить файл». Отправитель выбирает
один файл в системном окне. Получатель видит имя и размер, затем нажимает
«Выбрать место и принять». Существующий файл не заменяется — выбрать новое имя.
Отказ и отмена доступны отдельно от завершения всего сеанса.

Лимит — 1 ГиБ; данные идут частями по 64 КиБ. Полученный файл публикуется только
после проверки длины и SHA-256. Временный файл очищается при отмене, ошибке или
разрыве; успешный файл не открывается автоматически. Файловый путь не поступает
из сети и не передаётся в WebView. Управление мышью/клавиатурой не требуется для
обмена файлами, но каждый входящий файл требует собственного подтверждения.

Системный выбор/сохранение файлов подключён на desktop. На Android эти действия
пока отключены: интеграция Storage Access Framework остаётся отдельной работой.

## Показ экрана Android

После входящего запроса владелец нажимает «Разрешить», затем подтверждает системный
диалог Android. Система может предложить весь экран или отдельное приложение.
Без действующего системного разрешения и подтверждения запроса сеанс не включится.

MediaProjection работает через foreground service с действием остановки.
Остановить показ можно в Асси, системном индикаторе или уведомлении. Отзыв
разрешения завершает передачу. Токен не переиспользуется; для нового сеанса
согласие запрашивается заново. Удалённое управление самим Android не реализовано.

## Текущие границы

- Windows/macOS/Linux: desktop-адаптеры и файловые диалоги реализованы. Нативные
  сборки Windows/Linux и работа разрешений на этих ОС в этой среде не проверены.
- Linux Wayland: управление через RemoteDesktop portal не реализовано; X11
  поддерживается адаптером.
- Android: viewer и MediaProjection host для просмотра; файлы и управление
  Android ещё не подключены.
- Видео: software JPEG, до 1920 по длинной стороне, не аппаратный видеокодек;
  задержка, трафик и батарея на физических устройствах не измерены.
- Нет звука, нескольких мониторов, синхронизации раскладок/IME, secure desktop,
  unattended-доступа, аккаунтов/биллинга и подписанного публичного релиза.

Настоящие loopback-тесты покрывают nested TLS и файлы; системный захват экрана и
ввод в тестах не запускаются. До пилота обязательны физические проверки: два
устройства в разных сетях через свой relay, согласие/отказ/разрыв, Android rotation,
выбор приложения, блокировка экрана и остановка из системного индикатора.
